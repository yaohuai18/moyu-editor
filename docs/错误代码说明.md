# 错误代码说明

用户截图说「报错了」，你要干的第一件事是**去日志里搜一个字符串**。
这个字符串就是错误编号。

所有日志都是**单行 JSON**，格式固定：

```
[错误编号] {"userId":"...","projectId":"...","status":500,"detail":"PrismaClientKnownRequestError:P1001"}
```

- 前面方括号里是编号，直接搜这个
- 后面是**白名单字段**，只可能出现这些：
  `userId` / `projectId` / `chapterId` / `mode` / `status` / `durationMs` / `detail`
- **永远不会出现**：密码、Cookie、Authorization、API Key、用户正文、数据库连接串

`detail` 最多 200 字符，会被截断并压成一行（换行会破坏日志的一行一条结构）。

## 一、完整编号表

| 编号 | 什么情况 | 用户看到什么 | 该怎么办 |
| --- | --- | --- | --- |
| `AUTH_FAILED` | 未登录 / 会话失效 / 会话代次对不上 | 401「请先登录」 | 正常（重新登录即可）。**成片出现**要警惕：可能是有人在试别人的会话 |
| `LOGIN_FAILED` | 邮箱密码不对 | 登录页提示登录失败 | 零星正常。**成片出现 = 可能被撞库**，考虑加验证码或限制登录频率 |
| `REGISTER_FAILED` | 注册失败 | 注册页报错 | 看看是不是数据库问题 |
| `ACCOUNT_UPDATED` | 昵称被改（不是错误，留痕） | — | 不用管 |
| `PASSWORD_CHANGED` | 密码被改（不是错误，留痕） | — | 用户说「我没改密码」时，这是唯一能查的地方 |
| `PASSWORD_MISMATCH` | 改密码 / 注销时当前密码填错 | 400「当前密码不正确」 | 一个人反复出现 = 有人在猜密码（接口本身有 10 分钟 10 次的限制） |
| `ACCOUNT_DELETED` | 账号被注销（不是错误，留痕） | — | 日志里带 `projects` / `chapters` / `revisions` / `aiUsages` 四个数字，能看出删了多少 |
| `PROJECT_ACCESS_DENIED` | 作品不是你的（403） | 403「无权访问该作品」 | 零星是用户改 URL 试。**同一个人反复出现 = 有人在扫** |
| `PROJECT_NOT_FOUND` | 作品不存在（404） | 404 | 正常 |
| `CHAPTER_ACCESS_DENIED` | 章节不是你的 | 403 | 同上 |
| `CHAPTER_NOT_FOUND` | 章节不存在 | 404 | 正常。Prisma 的 `P2025`（要操作的记录没了）也归到这里 |
| `VALIDATION_FAILED` | 入参不合法（400） | 400 + 中文说明 | 正常。如果有人**刷**这个，说明在试参数 |
| `PAYLOAD_TOO_LARGE` | 正文超过单次上限（400） | 400「最多处理 N 字」 | 正常，提示用户分章 |
| `RATE_LIMITED` | 一分钟内调 AI 超过 10 次（429） | 429「请 N 秒后再试」 | 零星正常。**同一个人反复出现 = 有人在刷你的 Key 花钱** |
| `DAILY_QUOTA_EXCEEDED` | 今日 AI 额度用满（429） | 429「明天 0 点后恢复」 | 正常。整体额度经常满说明该调大或分级 |
| `VERSION_CONFLICT` | 别人先保存了同一章（409） | 409「内容已被更新，请刷新后确认」 | 正常。`detail` 里有 `client=x server=y`，能看出差了几版 |
| `AI_NOT_CONFIGURED` | 服务端没配 AI Key 或模型名（503） | 503「AI 服务尚未配置」 | **要看**：环境变量丢了，或者部署时漏配。网站其它功能不受影响 |
| `AI_PROVIDER_ERROR` | 上游报错（502） | 502「AI 处理失败」 | **要看**：集中 `401` = Key 失效；集中 `429` = 上游限流；集中 `5xx` = 上游故障 |
| `AI_INVALID_FORMAT` | 上游返回的内容解析不了（502） | 502 | 零星正常（模型偶尔不按格式输出）。成片 = 服务商改了返回格式 |
| `AI_EMPTY_RESPONSE` | 上游返回空（502） | 502 | 同上 |
| `DATABASE_ERROR` | 数据库出问题 | 500 | **必须看**。`detail` 里的 `P1001` = 连不上数据库；`P1008` = 连接超时/连接池满；`P2002` = 唯一约束冲突 |
| `UNKNOWN_ERROR` | 没归类的异常 | 500 | **任何一条都要当天看**，这是唯一可能藏着真 bug 的编号 |

## 二、几个排查套路

### 用户说「AI 不能用」

1. 日志搜 `AI_NOT_CONFIGURED` —— 有的话是环境变量丢了，去看 `/api/health`
2. 搜 `AI_PROVIDER_ERROR`，看 `detail` 里的上游状态码：
   - `401` → Key 失效或被作废，换 Key
   - `429` → 上游限流，等一会儿或者升配额
   - `500`/`502` → 上游故障，不是你的问题，先等着
3. 都没有？那可能是额度用满（搜 `DAILY_QUOTA_EXCEEDED`）或频率超了（搜 `RATE_LIMITED`）

### 用户说「我写的东西不见了」

1. 搜 `VERSION_CONFLICT`，看这个用户今天有没有出现过
2. 有 → 是并发保存被拦下了：内容没被覆盖，**还在版本历史里**，
   让他在编辑页右上角把历史版本翻出来
3. 没有 → 问他是不是清了浏览器数据；本地未保存的内容一旦页面关掉就真没了
   （自动保存是 1.2 秒防抖，关页面前有一次 `keepalive` 兜底）

### 用户说「页面打不开 / 一直转圈」

1. 外部拨测 `/api/health`：返回 503 就是数据库或环境变量的问题
2. 看有没有 `DATABASE_ERROR`；`P1001` 一般是数据库进程挂了或连接串错了
3. 都没有 → 看服务器进程还在不在（`systemctl status`），以及磁盘是不是满了

## 三、日志在哪

| 部署方式 | 去哪看 |
| --- | --- |
| systemd | `journalctl -u moyu -f` |
| pm2 | `pm2 logs moyu` |
| Docker | `docker logs -f <容器名>` |
| 托管平台（Vercel 等） | 平台的 Logs 页面，按关键字搜 |
| 本地 `npm run app` | 起服务的那个终端窗口 |

以后要接 Sentry 之类的服务，**只需要改 `src/lib/log.ts` 里 `logError` 一个函数**，
所有调用点自动跟着生效。这也是当初把它单独抽出来的原因。

## 四、编号是怎么定的（改代码前先看）

- **对外的 `code` 字段故意比内部日志粗**：
  用户不需要知道「是 P1001 还是 P2002」，只需要一个能在日志里搜到的标签。
  映射表在 `src/lib/log.ts` 的 `API_ERROR_CODES`
- 内部编号全量列表在同一个文件的 `ErrorCode` 类型里。
  **加新编号时同时改三处**：`ErrorCode` 类型、`API_ERROR_CODES`（如果要对外暴露）、
  这份文档
- 路由的 catch 块一律用 `logRouteError(error, { userId, projectId, ... })`，
  **不要写 `console.error(error)`** —— 那个写法会把整个异常对象连同堆栈丢进日志，
  而 Prisma 初始化异常的 message 里是带数据库连接串的，等于把密码写进日志文件
- 不要在路由里写 `error.message === "XXX"` 这种比较，一律用编号
