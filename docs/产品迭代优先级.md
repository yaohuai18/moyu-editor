# 产品迭代优先级

> 这份文档回答：**下一个版本做什么、为什么是这个顺序。**
> 排序原则：用户的刚需 > 数据安全 > 体验优化 > 锦上添花。

## 一、判断标准

一个需求进不进下一版，看三个问题：

1. **没有它用户会不会走？**（导出没有 = 作品被锁在站里，会走）
2. **不做会不会出事？**（备份没有定时 = 出事，属于运维不是功能）
3. **做完有多少人受益？**（逐条接受修改 = 重度用户天天用）

「老板觉得酷」不在这三条里。

## 二、下一版（v1.1 候选，按优先级排）

| 优先级 | 事项 | 为什么 |
| --- | --- | --- |
| ★★★ | **导出纯文本** | 用户带走自己作品的权利。没有导出，「云写作」=「人质」 |
| ★★★ | 长章节分段 + 队列 | 现在单次 50000 字上限，超长章节直接顶到天花板报错 |
| ★★☆ | 逐条（按句按段）接受修改 | 现在只能整篇接受/拒绝 AI 修改稿，重度用户嫌粗 |
| ★★☆ | 版本管理细化 | 内容没变不建版本、保存间隔限制、差异对比（现在只能整篇预览） |
| ★★☆ | 人物卡可视化编辑 + 禁用词编辑 | 字段在库里都有，就差界面 |
| ★☆☆ | AI 用量看板 | 台账数据都有了（`ops:ai` 是给老板的命令行版），用户侧还没有趋势图 |
| ★☆☆ | 忘记密码 / 邮箱验证 | 现在忘记密码只能找管理员手动改 |

## 三、明确不做的

- **绕过 AI 检测、伪装文本来源** —— 产品底线，别接这种需求，用户提了也婉拒
- **大改用户剧情的重写** —— 定位是轻度润色，不是代写
- **多人协作 / 评论批注** —— 单机 SQLite 撑不起，等搬 Postgres 且有真实需求再说

## 四、技术债（不是功能，但欠着要还）

| 债 | 影响 | 还法 |
| --- | --- | --- |
| 备份没有定时任务 | 生产库靠人记得备份 | Windows 计划任务跑 `npm run db:backup`，或上发布平台后用它的定时器 |
| 内存限流 | 多实例部署时限流形同虚设 | 上 Redis 之前不扩到多实例 |
| 内存日额度查询 | 每次调 AI 前查一次库 | 量大后再缓存 |
| `.env` 的 AUTH_SECRET 还是初始值 | 会话可被伪造 | **上线前必须换**（见下节） |
| 风格档案的 description/forbiddenWords 不能编辑 | 功能缺口 | 并进人物卡编辑那一批 |

## 五、上线前必做清单（提过多次，做完才能对外）

1. **作废泄露过的 AI Key**，重新生成填回 `.env`
2. **处理演示账号** `demo@moyu.local`（先把作品 `npm run works:move` 给真账号，再注销）
3. **换掉 `.env` 里的 `AUTH_SECRET`**（生成命令见 `.env.example`，换完所有人重新登录）
4. 配好 `OPS_EMAIL` / `OPS_PASSWORD` 探测账号（见 [运维手册](运维手册.md) 第六节）

## 六、每次动 backlog 的规矩

- 用户反馈进来的需求标「来自用户」，同类 3 次自动升优先级
- 砍需求可以，但要在本文档里留一行「为什么砍」，半年后别再捡起来重新讨论一遍
- 每次发版后把「下一版」这节实际完成情况抄进 [发布记录](发布记录.md)
