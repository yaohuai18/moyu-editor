# AI 用量监控

> 这份文档回答：**AI 花了多少钱、稳不稳、有没有人在刷、额度设计合不合理。**
> 报表命令：`npm run ops:ai`（默认最近 7 天，`npm run ops:ai -- --days=30` 看一个月）。

## 一、台账记了什么

每次调用 `/api/ai/edit`（成功、失败、被限流）都会在 `AiUsage` 表记一条：

| 字段 | 含义 |
| --- | --- |
| `mode` | diagnose（诊断）/ polish（润色） |
| `model` | 实际用的模型名 |
| `inputChars` / `outputChars` | 进出字符数（**不存正文**，正文太大也不该出现在统计表里） |
| `ok` | 成功没有。失败/被限流也记（`ok=false`），否则上游挂了报表上看不出来 |
| `durationMs` | 这次调用花了多久（第十一阶段起才有） |
| `errorCode` | 失败时的错误编号，和 [错误代码说明](错误代码说明.md) 同一套 |

**额度只认 `ok=true`**：失败的调用不扣用户次数（上游抖一次不能让用户白丢一次额度）。
改这张表的查询时务必确认 `ok` 过滤还在。

## 二、报表七节怎么用

| 节 | 正常长什么样 | 什么时候要行动 |
| --- | --- | --- |
| 每日调用量 | 有起伏、成功为主 | 连续多天失败列非 0 → 上游不稳，看下一节定位 |
| 失败明细 | 空，或少量 RATE_LIMITED | AI_ 开头的编号 ≥20 次 → 查 Key/上游状态 |
| 响应耗时 | 诊断 ~几秒、润色 ~十几秒 | 平均 >30 秒 → 用户会觉得卡死，考虑超时或分段 |
| 字符量 | 稳定增长 | 突然翻几倍 → 看高频用户那节是不是有人脚本刷 |
| 费用估算 | 量级参考 | 只用来发现突变，别拿去对账 |
| 高频用户 | 30 天几十次 | 30 天 ≥200 次 → 确认不是脚本刷接口 |
| 额度用满 | 0~几个人 | 每天都同一批人满 → 考虑分级额度 |

## 三、费用估算的口径

默认按「输入 ¥1.5 / 输出 ¥5 每百万字符」估，来源是 DeepSeek V3
token 单价的粗折算（1 汉字 ≈ 0.6 token）。**这是量级参考，不是账单**：
真实计费按 token、进出单价不同、还有缓存折扣。

要改单价就在 `.env` 里配（不配用默认值）：

```
AI_COST_INPUT_PER_M=1.5
AI_COST_OUTPUT_PER_M=5
```

## 四、隐私口径

- 台账**不存正文**，只存字符数
- 报表里的用户邮箱打码成 `ab***@domain` —— 报表经常被截图发群里，
  完整邮箱没必要出现
- 报表文件在 `ops-reports/`，不要整个目录上传到公开场合
  （虽然里面没有密钥，但有用量分布）

## 五、额度与限流的现行参数

| 机制 | 参数 | 改哪里 |
| --- | --- | --- |
| 每分钟限流 | 10 次/分钟/人 | `src/app/api/ai/edit/route.ts` 顶部 |
| 每日额度 | 30 次/天/人（只数成功） | `src/lib/ai-usage.ts` 的 `DAILY_AI_LIMIT` |
| 单次长度上限 | 50000 字 | 同 edit 接口的 zod 校验 |

改额度后要重新构建部署才生效。

## 六、什么时候怀疑被刷

三个信号同时出现基本可以定性：

1. 高频用户那节有人 30 天 ≥200 次
2. 失败明细里他的 `RATE_LIMITED`（每分钟限流）占大头 —— 人手点是点不出限流的
3. 字符量曲线在固定时段陡增

处理顺序：先看他的失败构成（正常写作不会大量触发限流）→
确认是脚本 → 改密码/封号（`npm run works:move` 先把作品转走再注销）。
