# 备份与恢复说明

**没演练过的备份，不算备份。** 这份文档的重点不是"怎么复制文件"，
而是"怎么确认这份备份真能用"。

---

## 一、备份

### 本地 SQLite

```bash
npm run db:backup
```

备份文件落在 `backups/`（已在 `.gitignore` 里，不进 Git），
文件名带时间戳，例如 `backups/dev-20260925-231500.db`。

**脚本里有一个不能省的细节**：先把 WAL 里的内容落盘（`PRAGMA wal_checkpoint(FULL)`）
再复制。SQLite 开着 WAL 模式时，最近几次写入还在 `dev.db-wal` 里，
直接 copy `dev.db` 会备份出一个"稍微旧一点"的库 —— 丢的正好是你最后写的那段。

### 托管数据库（Postgres 等）

不用这个脚本。用供应商的自动备份（云数据库基本都带），
或者按脚本末尾打印的命令用 `pg_dump` 手动导。

### 什么时候必须备份

- **每次执行迁移之前**（尤其是删字段、改结构的那种）
- 每次发布之前
- 定期（按你的数据价值定，个人项目一天一次够；有人真在用就上自动备份）

### 备份放哪

同一块盘上的备份，盘坏了就一起没了。真正的做法是：

1. 本地一份（快速恢复用）
2. 云对象存储 / 另一台机器一份（防硬件故障）

个人项目至少把 `backups/` 目录定期同步到网盘或对象存储。

## 二、恢复演练（定期做，别等出事才试）

```bash
npm run db:restore-drill
```

它做的是完整体检，六步：

```
1. 造一批带标记的演练数据（账号 / 作品 / 2 章 / 4 条版本 / 人物卡 / 风格档案）
2. 落盘 WAL，复制出一个备份
3. 在**独立的库文件**里打开这份备份（绝不动 prisma/dev.db）
4. 核对 5 张表的记录数与源库一致
5. 校验关系链没断（版本 → 章节 → 作品 → 用户）
6. 用 bcrypt 对着恢复库里的哈希**重新验一次密码** → 确认恢复后登得上
   然后读一遍正文，确认内容真的在
7. 删干净演练数据
```

三条硬规矩写在脚本注释里：

- **不碰生产库的恢复**：恢复出来的库单独打开，绝不会覆盖 `prisma/dev.db`
- **演练数据带明显标记**（`drill@moyu.local`），跑完就删
- **必须校验密码能验通**，而不只是"这条记录还在" ——
  恢复后登不上是最常见的翻车方式

全绿的样子：`19 / 19`（每项一行 `[PASS]`）。

## 三、真出事了：恢复步骤

**先停服务，别让它在恢复过程中继续写。**

```bash
# 1. 停服务
sudo systemctl stop moyu

# 2. 把现在的库挪走（不是删！万一是误判还能回头）
mv prisma/dev.db prisma/dev.db.broken-$(date +%Y%m%d-%H%M%S)

# 3. 把备份复制回来
cp backups/dev-20260925-231500.db prisma/dev.db

# 4. 清掉可能残留的 WAL（它属于刚才那个被挪走的库）
rm -f prisma/dev.db-wal prisma/dev.db-shm

# 5. 确认结构跟当前代码匹配（迁移都应用过）
npm run db:deploy

# 6. 起服务
sudo systemctl start moyu

# 7. 验
curl -s http://127.0.0.1:3000/api/health
```

**恢复后必须自己登一次**，别只看健康检查 ——
健康检查只证明数据库连得上，不证明你的账号和正文还在。

Postgres 的恢复：用供应商控制台的"按时间点恢复"，或 `pg_restore`。

---

## 四、恢复之后的三件事

1. **告诉用户**：如果丢了最近一段时间的改动，按 [回滚方案](回滚方案.md) 里的模板发通知
2. **查原因**：是误删、磁盘坏了、还是迁移写错了？不查清楚还会再发生
3. **看备份策略**：这次丢了多少？间隔多久备份一次才够？

---

## 五、几个容易忽略的点

| 坑 | 说明 |
| --- | --- |
| 只备份了 `dev.db`，没落 WAL | 丢最后几次写入。脚本已经处理了，手动 copy 时要记得 |
| 恢复了库，但结构比代码旧 | 起服务前先 `npm run db:deploy` |
| 恢复了库，但环境变量不一样 | `AUTH_SECRET` 变了的话，所有人的登录态失效 —— 这不是故障，是预期行为 |
| 备份文件没加密 | 里面有用户的正文和密码哈希。放对象存储时记得开加密，权限设成私有 |
| 演练只在有空的时候做 | 改成定期做。没演练过的备份，出事时才发现打不开的概率不低 |
