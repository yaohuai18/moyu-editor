# 回滚方案

上线之后发现不对，按这份走。**先止损，再查原因。**
用户不会因为你查得快而原谅网站不能写，但会因为你一直在修而看到「一直坏着」。

---

## 〇、判断该走哪条

| 症状 | 走哪条 | 目标 |
| --- | --- | --- |
| AI 在烧钱 / 上游挂了 / Key 泄露 | **第一节：停 AI** | 30 秒内止血，网站照常能写字 |
| 新版本有 bug（页面报错、功能不对） | **第二节：回滚应用** | 退回上一版，数据不动 |
| 数据库被写坏了 / 误删数据 / 迁移写错 | **第三节：恢复备份** | 用备份救回来 |
| 数据库结构改错了（列没了、类型不对） | **第四节：回滚迁移** | 先备份，再改结构 |

---

## 一、停 AI（最快的止损）

**AI 是唯一会持续花钱、持续出错的模块，而且停了它网站完全能用。**

```bash
# systemd 的写法：把 Key 清空后重启（Key 空 → AI 接口返回 503，其他功能不受影响）
sudo systemctl edit moyu
# 在打开的编辑器里加：
#   [Service]
#   Environment="AI_API_KEY=" "AI_MODEL="
sudo systemctl restart moyu
```

或者在部署平台的环境变量页把 `AI_API_KEY` 删掉再重新部署。

验一下：

```bash
curl -s http://127.0.0.1:3000/api/health   # aiConfigured 会变成 false
```

`aiConfigured: false` 是**预期状态**，不算故障 —— 登录、写小说、版本历史全部照常。

**还有什么不用改代码就能调的**：

- AI 额度太松（有人在刷）：`src/lib/ai-usage.ts` 里的 `DAILY_AI_LIMIT`（默认 30）改小
- 频率限制太松：`src/app/api/ai/edit/route.ts` 里的 `RATE_LIMIT`（默认每分钟 10 次）改小
  改这两个数字要重新构建 + 重启。

## 二、回滚应用版本

**应用版本可以直接退，数据库最好别动。**

### 有版本标签（推荐的前提）

发布时打了 tag 的话：

```bash
git fetch --tags
git checkout v1.0.0            # 上一个可用版本
npm install                    # 依赖可能变了，必须重装
npm run build
sudo systemctl restart moyu
curl -s http://127.0.0.1:3000/api/health
```

### 没有标签

```bash
git log --oneline -20          # 找到上一个好的 commit
git checkout <那个 commit>
npm install && npm run build
sudo systemctl restart moyu
```

### 重要的前提：新迁移必须是"只加不改"

回滚应用**只有在数据库结构向前兼容时**才安全。判断标准：

| 新迁移做了什么 | 能不能只退应用 |
| --- | --- |
| `ADD COLUMN`（加列，有默认值） | ✅ 能。旧代码看不见新列，照常跑 |
| `CREATE INDEX` | ✅ 能。索引多了不影响旧代码 |
| `ADD TABLE` | ✅ 能。旧代码不用它 |
| `DROP COLUMN` / 改名 | ❌ 不能。旧代码读不到那一列，直接报错 |
| 改数据类型 / 拆表 / 合并表 | ❌ 不能。必须先恢复备份 |

⚠️ **第十阶段/第九阶段加的三列都是"只加"类型，可以安全地只退应用：**
`Chapter.version`、`User.tokenVersion`、`Revision.chars`。

### 退应用之后要验的四件事

1. `/api/health` 返回 200
2. 能登录
3. 能打开一个作品、能保存（看看版本历史有没有新增）
4. 编辑器里 AI 两个按钮的行为跟这一版代码一致

## 三、恢复数据库备份

**只有确认数据真坏了才走这条。** 恢复会丢掉"备份时间点之后的所有改动"。

详细步骤见 [备份与恢复说明](备份与恢复说明.md) 第三节。要点：

```bash
sudo systemctl stop moyu
mv prisma/dev.db prisma/dev.db.broken-$(date +%Y%m%d-%H%M%S)   # 挪走，不是删
cp backups/dev-<时间戳>.db prisma/dev.db
rm -f prisma/dev.db-wal prisma/dev.db-shm
npm run db:deploy
sudo systemctl start moyu
```

**恢复完自己登一次**，确认账号和正文真的在 —— 健康检查证明不了这个。

## 四、回滚数据库迁移

先说结论：**Prisma 没有"自动回滚迁移"这个功能**（它的 `migrate resolve` 只改记录状态，不改结构）。
所谓回滚，本质是**写一个新的前向迁移把结构改回去**。

步骤：

1. **先备份**：`npm run db:backup`（不备份就动结构，是在赌）
2. 想清楚目标结构是什么 —— 是回到上一版，还是只是修掉某个错列？
3. 改 `prisma/schema.prisma`，让它描述**你想要的结构**
4. 生成新迁移：`npm run db:migrate -- --name rollback_xxx`
5. 看一遍生成的 SQL（`prisma/migrations/<时间戳>_rollback_xxx/migration.sql`），
   确认它没有 `DROP TABLE` 之类你没想到的东西
6. 生产上执行：`npm run db:deploy`
7. 重启服务

**如果第 5 步发现它会删掉列里的数据**，那就不是"回滚"而是"数据丢失"了。
这种情况下要问的是：这些数据还要不要？要的话先导出来再删列。

## 五、通知用户

**只要用户能感觉到（登不上、内容变了、功能没了），就要说一声。**
不说的话，用户第一反应是"这网站不靠谱"。

### 模板 A：功能临时不可用

> 【墨语编辑器】AI 诊断 / 润色功能暂时不可用，正在修复。
> 登录、写小说、保存、版本历史都正常，不受影响。
> 预计 X 小时内恢复。

### 模板 B：维护窗口

> 【墨语编辑器】今晚 23:00–23:30 做一次维护，期间可能无法保存。
> 请在 23:00 前确认编辑器右上角显示「已保存」。
> 未保存的内容建议先复制一份到本地。

### 模板 C：可能丢了一部分内容（最难开口，但必须说清）

> 【墨语编辑器】X 月 X 日 XX:XX—XX:XX 之间的改动可能没有保存成功。
> 请您打开作品，检查一下这段时间写的内容。
> 如果缺了，点编辑页右侧的「版本历史」，那里保留了每次保存的快照，可以逐条查看和恢复。
> 给您造成麻烦，抱歉。

模板 C 里那句"去版本历史找"不是场面话 ——
**每次保存都会留一条版本记录**，这是这个项目最大的兜底能力。
只要保存过一次，内容就在库里。

## 六、任何一次回滚之后

1. 在 [发布记录](发布记录.md) 里补一行：回了哪个版本、为什么、现在什么状态
2. 写清楚"已知问题"：这次回滚留下什么尾巴（比如某个迁移没回、某个功能暂时关着）
3. 查清根因。同一处回滚两次，说明问题在流程里，不在代码里 ——
   那就是"发布前少了哪一步验证"的问题
