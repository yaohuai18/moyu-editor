# 功能 07：AI 诊断 / 润色

## 成本先说清楚

- 真实调用走 `POST /api/ai/edit`，用 `.env` 里的 `AI_API_KEY` 打真实模型，**按 token 计费**。
- 每次调用会写一条 `AiUsage` 记录，只有 `ok=true` 才扣当日次数。
- 默认每日上限 **30 次**（面板显示 `今日 AI 用量 N / 30 次`）。
- **验证不要用真 key**。两条替代路线：
  1. `scripts/api-test.mjs` 自带一个假 AI 服务（端口 `11499`，`FAKE_AI_PORT` 可改），但它只在接口测试里起；
  2. 更省事：**不验 AI 的内容质量，只验「按钮能点、状态会变、次数会记」**——用真 key 跑 1-2 次即可，别做批量。

写验证技能的目的是抓回归，不是评测模型。**AI 生成的文本好不好，进不了自动断言**，不要试图验这个。

## 页面结构（编辑页右侧面板）

```
今日 AI 用量 0 / 30 次

文本诊断
[开始诊断]          ← 执行中变「分析中…」

轻度润色
[生成润色稿]        ← 执行中变「生成中…」

（有结果时出现）润色结果
（禁用词提示）禁用词已接入 AI（诊断与润色会尽量避开这些词）；编辑功能排在后面的阶段。
```

执行期间全页状态灯显示 `AI 处理中（诊断）` / `AI 处理中（润色）`。

诊断结果里可能带一个「模板化程度」评分（0-100，越低越自然，服务端已钳制到整数），以及形如 `模板化严重，建议整段重写后再润色` 的结论标签。

## 该验什么

| 项 | 断言 | 值不值得验 |
|---|---|---|
| 按钮存在且能点 | 出现 `分析中…` / `生成中…` | ✅ 值得（改 UI 常碰） |
| 空正文时不乱调 | 正文为空点诊断 → 应给提示，不该白扣一次额度 | ✅ 值得 |
| 次数会 +1 | 成功一次后 `今日 AI 用量` 从 `N` 变 `N+1` | ✅ 值得 |
| 达上限会拦 | 把 used 造到 limit → 点按钮出现 `今日 AI 使用次数已达上限，明天 0 点后恢复` | ⭕ 有改动时验 |
| 生成内容质量 | — | ❌ **不要验** |
| 禁用词真的避开 | — | ❌ 不要验（模型的，测不稳） |

**次数 +1 的查库验法**（比看界面可靠）：

```js
// 用 probe-db.cjs 的同一套连接方式
const before = await prisma.aiUsage.count({ where: { userId } });
// …点一次诊断…
const after = await prisma.aiUsage.count({ where: { userId } });
// after === before + 1，且最新一条 ok === true
```

## 换章会清空结果（这条容易当成 bug 报上来）

`editor-client.tsx:605` 注释原文：

> 换章时清掉上一章的诊断/润色结果与打开的版本预览，避免张冠李戴。

所以：切到另一章，右侧的诊断结果消失是**正确行为**，不是 bug。切回来也不会恢复（结果不落库）。

---

## 已知限制

1. **没有假 AI 就无法在沙箱里跑通全链**。`api-test.mjs` 的假服务是给它自己用的，`next start` 起的站点仍会读 `.env` 里的真 key。
2. 想彻底不花钱地验「按钮 → 状态 → 次数」，可以临时把 `AI_BASE_URL` 指向本地假服务（改 `.env` 属禁止改动文件，**必须你本人改，且改完要改回**）。
3. `AiUsage` 有 `errorCode` 字段——失败也会记一条（`ok=false`）。所以「次数没变但多了一条记录」是正常的。
